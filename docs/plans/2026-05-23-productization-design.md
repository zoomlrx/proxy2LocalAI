# Proxy2LocalAI 产品化设计文档 V1.1

## 设计目标

Proxy2LocalAI 的下一阶段目标不是继续堆叠高级能力，而是解决三个核心问题：

1. 用户第一次能快速成功。
2. 请求失败时用户知道卡在哪里。
3. 通用能力通过模板和分层 UI 暴露，而不是把复杂配置直接甩给用户。

产品定位保持不变：Proxy2LocalAI 是一个面向开发、调试、测试场景的本地 AI API 替身，用浏览器扩展拦截指定线上接口，再由本地 Bridge 调用 Claude Code、Codex 或自定义 CLI 返回兼容响应。

## 一、核心设计原则

### 1. 任务优先，而不是配置优先

用户不是来“填 profile”的，而是来完成一件事：

> 把这个接口临时接到我的本地 AI。

因此 UI 第一层应该围绕任务组织：

- 粘贴 cURL。
- 选择本地 AI。
- 选择本地 AI 配置项目路径。
- 测试代理。
- 启用规则。

高级字段默认折叠。

### 2. 失败必须可解释

任何失败都必须能被归类：

- 扩展没命中规则。
- Bridge 未启动。
- profile 未同步。
- token 不匹配。
- CORS 或预检失败。
- 本地 CLI 未找到。
- 本地 CLI 启动了但无有效输出。
- provider 超时或被取消。
- 响应映射失败。

用户不应该通过翻 `requests.log` 才知道原因。

### 3. 通用性靠模板，不靠用户手写协议

自定义 JSON、SSE 映射、OpenAI 兼容响应是核心能力，但普通用户不应该直接面对底层字段。

应提供模板：

- OpenAI Chat Completions。
- OpenAI SSE。
- 普通业务 JSON：`{ code, data, message }`。
- 通用 SSE：`message / reasoning / done`。
- 从真实响应样例生成模板。

### 4. 安全默认保守

默认只代理显式接口，只监听 `127.0.0.1`，默认过滤敏感请求头，默认不开启危险 CLI 权限。任何危险能力都必须二次确认。

## 二、关键产品模块

### 1. 首次上手向导

新增“创建代理向导”，替代用户第一次面对完整配置表单。

流程：

1. 检测 Bridge：显示 Bridge 地址、在线状态、版本、profile 数量。Bridge 不在线时，展示当前系统对应的启动命令。
2. 粘贴 cURL：自动解析目标地址、接口路径、HTTP 方法、请求头、请求体样例。
3. 选择本地 AI：选择 Claude Code、Codex 或 Custom。默认 Claude Code。
4. 选择本地 AI 配置项目路径：说明该路径决定 `.claude`、`CLAUDE.md`、Codex 配置等项目级上下文。
5. 选择返回格式：默认 OpenAI SSE。可切换普通 JSON 或模板响应。
6. 测试代理：用 cURL 样例参数发起一次本地测试，展示命中、Bridge、AI、响应四段状态。

成功标准：用户不用打开 DevTools，也能看到“第一次代理成功”。

### 2. 最近请求调试台

新增“最近请求”面板，显示最近 20 条代理请求。

每条记录包含：

- 时间。
- 命中的 profile。
- 原始 URL 和 method。
- 页面 URL。
- Bridge 状态。
- Provider 状态。
- 首包耗时。
- 总耗时。
- 返回模式。
- 最终状态。

点击详情后展示：

- 请求上下文摘要。
- 实际 prompt 预览，敏感字段脱敏。
- provider 命令摘要。
- stdout 阶段摘要。
- 返回内容预览。
- 错误归因。
- 一键复制诊断信息。

这个模块是“好用”的核心。它让用户知道 Claude/Codex 到底有没有被调用、有无输出、卡在哪个阶段。

### 3. 配置页信息架构重组

Options 页面改为三层：

- 基础配置：名称、启用状态、目标接口、HTTP 方法、本地 AI、项目路径、返回格式、提示词。
- 高级配置：超时、请求体上限、上下文正则、多轮记忆、provider 追加参数、敏感字段过滤。
- 专家配置：custom provider、自定义 JSON 模板、SSE 事件映射、危险 CLI 权限。

默认只展开基础配置。高级和专家配置需要用户主动打开。

### 4. 响应模板系统

新增“响应格式模板”概念。

每个模板定义：

- 模板名称。
- 适用类型：`block`、`stream`、`custom_json`、`mapped_sse`。
- AI 文本插入位置。
- done 事件格式。
- 错误响应格式。
- 示例预览。

用户可以：

- 选择内置模板。
- 粘贴真实接口响应样例生成模板。
- 保存为自定义模板。
- 导出模板给别人。

这会把当前“强但难配”的通用能力变成“可选择、可预览、可复用”。

### 5. Provider 可靠性设计

每个 provider 都需要独立诊断状态。

Claude Code / Codex 应显示：

- CLI 是否存在。
- 当前执行目录是否存在。
- 实际命令摘要。
- 是否启用危险权限。
- 是否禁用工具调用。
- 是否收到 stdout。
- 是否解析到有效 assistant 输出。

Provider 测试分两种：

- 轻量测试：只检测命令存在，不消耗模型额度。
- 实际测试：发送最小 prompt，确认能返回文本。

Custom Provider 需要明确提示：这是本地命令执行能力，只适合可信命令。

## 三、数据与接口设计

### Profile 继续作为核心配置单元

保留现有字段，新增或明确以下概念：

- `setupMode`：`wizard` 或 `advanced`，用于 UI 回放用户创建来源。
- `responseTemplateId`：当前选择的响应模板。
- `sensitiveHeaderPolicy`：敏感头过滤策略。
- `debugEnabled`：是否记录详细调试信息。
- `lastTestResult`：最近一次测试摘要，只用于 UI 展示。

### Bridge 新增诊断接口

建议新增：

- `GET /diagnostics/recent`：获取最近请求列表。
- `GET /diagnostics/recent/:requestId`：获取某条请求详情。
- `POST /admin/test-profile/:profileId`：使用 profile 执行一次测试代理。
- `POST /admin/parse-curl`：可选。也可以继续放在扩展端解析。

诊断信息默认只保存在内存，避免长期落盘敏感数据。用户点击“导出诊断包”时才生成脱敏文本。

## 四、交互设计要求

### Popup

Popup 不再只是状态摘要，应提供快速判断：

- Bridge 在线或离线。
- 已启用 profile 数量。
- 最近一次请求状态。
- 快捷入口：打开配置、打开最近请求、同步规则。

### Options

Options 是主控制台，左侧 profile，右侧配置与调试。

推荐结构：

- 顶部：Bridge 状态条。
- 左侧：profile 列表。
- 中间：当前 profile 配置。
- 右侧或底部：最近请求和测试结果。

### 侧边配置栏

侧边配置栏不应继续承担完整表单编辑职责。它的定位是“当前配置摘要、运行状态、安全策略和轻量操作”，用于帮助用户快速确认当前选中对象是否正确、安全、可用。完整配置、复杂字段、长 JSON、响应映射、Provider 细节和危险能力应进入主编辑区、抽屉或弹窗。

推荐结构：

- 当前配置：名称、启用状态、Provider、响应协议、项目路径。
- 映射状态：规则数、已启用规则数、预览状态、最近一次测试结果。
- 安全策略：预览脱敏、输出 tool 事件、允许 `raw/data` 变量、是否持久化渲染帧。
- 诊断摘要：最近请求时间、最近失败阶段、复制诊断入口。

布局规范：

- 宽度建议控制在 `320px` 到 `360px`。
- 外层内边距统一为 `16px`，分组间距为 `12px` 到 `16px`。
- 分组只承载单一主题，避免在侧栏中继续嵌套复杂卡片。
- 摘要字段使用 key-value 列表，不展示成可编辑表单。
- 长 URL、长路径、长错误和长响应必须单行截断或多行折叠，并提供复制入口；不得撑开侧栏宽度。
- 侧栏内只保留“查看详情”“复制诊断”“打开完整配置”等轻操作；保存、测试、应用、同步等主操作应放在主内容区或抽屉底部。

开关规范：

- 用于启用、关闭、允许、禁止的布尔能力统一使用 Switch，不再使用默认 checkbox。
- Switch 文案放在控件左侧或上方，不写在开关内部。
- Switch 建议尺寸为 `36px * 20px`，圆点为 `16px`，内距为 `2px`。
- 开启状态使用 primary 或 success 色；高风险能力开启时使用 warning 色，并显示短风险提示。
- 关闭状态使用 muted 轨道和清晰圆点；禁用状态降低透明度但仍能识别当前状态。
- 所有 Switch 必须支持键盘操作、可见 `focus-visible` 状态和可访问名称。

高风险策略：

- `raw/data` 变量、tool 输入输出、危险 CLI 参数、自定义命令等能力必须与普通配置视觉隔离。
- 高风险项默认关闭，开启后显示短提示，例如“已放宽安全边界，预览和诊断中可能出现敏感内容。”
- 颜色不能作为唯一风险表达，必须同时提供文本、图标或标签。

### 状态文案

必须从内部术语转为用户动作语言：

- “DNR 规则”显示为“浏览器拦截规则”。
- “profile 未同步”显示为“配置尚未同步到本地 Bridge”。
- “provider stdout”显示为“本地 AI 已产生输出”。
- “not_found”显示为“Bridge 没找到这条代理配置”。

## 五、验收标准

### 首次上手验收

- 新用户能在 5 分钟内完成一次 demo API 代理。
- 不需要手动编辑 JSON。
- 不需要打开 DevTools。
- Bridge 未启动时能看到明确启动命令。

### 调试验收

- 任意一次代理失败，都能在 UI 中看到失败阶段。
- 能复制一份脱敏诊断信息。
- 能区分“没命中规则”和“AI 没返回”。

### 通用性验收

- 至少内置 4 类响应模板。
- 用户能从 cURL 创建配置。
- 用户能从真实响应样例预览包装后的返回。
- SSE 和普通 JSON 都能被测试面板验证。

### 安全验收

- 默认不传入 `authorization`、`cookie` 等敏感头到 prompt，除非用户显式允许。
- 危险 CLI 权限默认关闭。
- 导出模板默认移除 token、本地路径，并停用 profile。
- 诊断信息导出前必须脱敏。

### 侧边配置栏验收

- 侧边配置栏在 `320px` 宽度下不出现横向滚动。
- 配置摘要、状态、安全策略和诊断摘要分区清晰，用户能在 5 秒内判断当前配置是否启用、使用哪个 Provider、返回什么协议。
- 所有布尔控制使用统一 Switch 样式，不使用裸 checkbox 表达启停状态。
- 高风险开关开启后必须出现风险提示，且不能只依赖颜色表达风险。
- 长路径、长 URL、长错误和长响应不会撑破布局，并支持复制或查看详情。
- 复杂配置详情不直接铺在侧栏，必须进入主编辑区、抽屉或弹窗。
- 侧栏内所有可点击元素支持键盘操作，焦点状态清晰可见。

## 六、推荐路线图

### P0：让用户第一次成功

- 首次创建向导。
- cURL 解析增强。
- 测试代理按钮。
- Bridge 离线启动提示。
- 基础配置和高级配置分层。

### P1：让失败可解释

- 最近请求调试台。
- 请求阶段状态模型。
- 诊断包导出。
- Provider 轻量检测与实际检测。

### P2：让通用性可用

- 响应模板系统。
- 从真实响应样例生成模板。
- SSE 映射可视化。
- OpenAI、普通业务 JSON、通用 SSE 模板。

### P3：让安装更像产品

- release 包优化。
- Windows/macOS/Linux 启动器。
- Bridge 版本与扩展版本兼容检查。
- 后续评估 Native Messaging 或单文件 Bridge。

## 七、设计结论

Proxy2LocalAI 下一阶段最重要的不是增加更多 provider，也不是继续扩大配置模型，而是建立三个闭环：

1. 创建闭环：用户知道怎么配置，并能第一次成功。
2. 诊断闭环：失败后用户知道哪里错了。
3. 模板闭环：复杂协议可以被复用，而不是每次手写。

只要这三个闭环完成，这个项目就会从“强大的工程工具”升级为“可长期使用的开发者产品”。
